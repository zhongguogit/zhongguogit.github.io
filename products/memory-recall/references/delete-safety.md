# 删除安全协议（预览 / 确认 / 墓碑 / 撤回）

> 用户的原话是："说话把哪些特征的之前的东西全部给删光，这样不容易导致保存下来的反而是废物。"
>
> 但"删光"是**不可逆**的动作。这一份定义：怎么删得干净，又不会删错。

---

## 一、五步协议（缺一步都不许执行）

```
① 预览  →  ② 确认  →  ③ 进回收区  →  ④ 留墓碑  →  ⑤ 彻底清除
```

| 步 | 谁做 | 必须看到什么 |
|---|---|---|
| ① 预览 | 系统 | 命中条目的编号 + 摘要（不是"3 条"这种数字） |
| ② 确认 | 用户 | 回一个字「删」或 `--yes`；不回 = 取消 |
| ③ 回收区 | 系统 | 打印"已进回收区，24 小时内可 undo" |
| ④ 墓碑 | 系统 | 索引留一行 `M-xxx 已删除 2026-10-18`（只留"曾经有过"，不留内容） |
| ⑤ 彻底清除 | 用户/超时 | `purge` 或 24 小时后自动清空 |

---

## 二、预览的输出格式（固定）

```
🗑 将要删除 3 条（含「老周」）：
   ① M-20261018-001 与老周谈定代发，佣金 8%
   ② M-20261005-007 老周第一次问价
   ③ M-20260920-003 认识老周
⚠ 删了之后 24 小时内可撤回；24 小时后彻底清除
⬆️ 回「确认删」执行 ｜ 不动就是取消
```

**要求**：
- 每条必须有**摘要**，不能只有 ID（用户记不住 ID）；
- 必须显示**总数**；
- 必须显示**撤回窗口**；
- 默认不动 = 取消（不做"沉默即同意"）。

---

## 三、墓碑机制（为什么删了还要留一行）

用户说"删光，不留废物"，但一个月后可能又问："我是不是跟老周谈过？"

这时候：

- **有墓碑** → "跟老周有过 3 条记录，你 10-18 删了" → 他知道自己删过，可以去找别处的备份；
- **没墓碑** → "没找到老周" → 他以为从没谈过，可能重复踩坑。

**墓碑只存四个字段**：

```json
{"id": "M-20261018-001", "deleted_at": "2026-10-18T15:30:00", "title": "老周代发", "level": "重要"}
```

**绝不存**：L1 原文、L2 摘要、L3 标签里的隐私内容。

> 墓碑文件：`~/.memory-recall/tombstones.json`。可随时 `purge --tombstones` 一并清除。

---

## 四、撤回（24 小时窗口）

### 4.1 机制

删除时不真删，整条记录搬到 `trash.json`，打上 `_deleted_at` 时间戳。

```python
for m in hits:
    m["_deleted_at"] = ts
    trash.append(m)
```

### 4.2 撤回

```
$ mem.py undo
↩️ 已恢复 2 条，1 条已超 24 小时无法恢复
```

**规则**：
- 只恢复 24 小时内的；
- 超时的**留在回收区**（不自动删，等 `purge`），但要明确告诉用户"这几条恢复不了"；
- 撤回后 `_deleted_at` 字段要清掉，否则下次统计会错。

### 4.3 为什么是 24 小时

- 太短（1 小时）：用户睡一觉就过期了；
- 太长（7 天）：回收区变成"第二个数据库"，等于没删；
- **24 小时** ≈ "一个工作日"，够他发现删错。

---

## 五、彻底清除

### 5.1 手动

```
$ mem.py purge
🧹 回收区已清空（3 条彻底删除）
```

### 5.2 自动

每次启动时检查回收区，超过 24 小时的条目**不自动删**（保守），但 `stats` 会提示：

```
📊 记忆 12 条 ｜ 回收区 3 条（其中 2 条已超 24 小时，建议 purge）
```

> **设计取舍**：宁可多占几 KB，也不要自动删掉用户可能还想恢复的东西。磁盘便宜，信任贵。

## 六、危险操作：清空全部

```
用户：清空全部记忆
```

**必须走这条路**：

```
⚠ 这是清空**全部**记忆，不是删某几条。
   当前共 12 条（重要 3 条 / 一般 7 条 / 背景 2 条）

   如果只是想删一部分，告诉我特征词，我按特征删。
   如果确实要全清：
     ① 先备份：mem.py backup
     ② 回「确认清空全部」四个字

   ⬆️ 不动就是取消
```

**要求**：
1. **先提示备份**，并给出备份命令；
2. **要求输入确认短语**（不是"是/否"）；
3. **必须列出将被删的分布**（重要几条），让他知道损失什么。

---

## 七、按特征删的边界

| 用户说 | 删什么 | 不删什么 |
|---|---|---|
| "删掉关于老周的" | L3 含 `老周` 的全部 | 只是文中提一句"老周介绍的"的（除非也命中） |
| "删掉 10 月之前的所有" | `at < 2026-10-01` 的全部 | 墓碑（墓碑保留"曾有过"） |
| "删掉没用的" | `level == 背景` 且 30 天未访问 | 任何 `重要` 级别 |
| "删掉那个卡住的事" | 含 `卡住` 事件的条目 | —（这条风险高，预览时必须逐条确认） |

### 7.1 "老周"这种跨条目特征，删之前要提醒影响面

```
🗑 将要删除 3 条（含「老周」）：
   ...
⚠ 提醒：这 3 条里有 1 条是「重要」级别（含佣金 8% 的谈定）。
   删了之后，这笔账在记忆里就没有依据了。
```

---

## 八、绝不做的四件事

1. **不在没预览的情况下删**——哪怕用户说"直接删"；
2. **不静默删**——不因为"过期""低价值"自动删掉任何一条；
3. **不留隐藏副本**——24 小时撤回期过后是真删，不做"其实还在某个角落"这种事；
4. **不删墓碑**——除非用户明确说"连删除记录一起清"。

---

## 九、命令对照

```bash
python mem.py rm 老周            # ① 预览
python mem.py rm 老周 --yes      # ②③ 执行（进回收区）
python mem.py undo               # ④ 24 小时内撤回
python mem.py purge              # ⑤ 彻底清除
python mem.py stats              # 看回收区还剩多少
```
